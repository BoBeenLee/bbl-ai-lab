# Log

## 2026-09-18

- **DGX hermes 의 비전 백엔드를 Cloudflare Workers AI 로 옮겼다.** `auxiliary.vision` 이
  `custom:cfai` + `@cf/qwen/qwen3.8-27b`, 폴백은 OpenRouter `inclusionai/ling-3.0-flash-vl:free`.
  무료 후보를 전수 실측해 고른 결과다 (합성 영문 OCR·도형, 합성 한국어 공지, 실제 일러스트 3종).
  계정이 Workers **Free** plan 이라 하루 10,000 neurons 가 공짜고, 실측 610 prompt + 147 completion
  토큰이 약 68 neurons 이니 **하루 145콜쯤 된다**. 초과하면 `3036` 429 로 거절될 뿐 과금되지 않는다.
  쫓아낸 로컬 `llama-local` 과 **같은 qwen3.8-27b 인데 6초 대 45~66초**다. 로컬 GPU 가 ComfyUI 와
  직렬로 도는 값을 그대로 치르고 있었다.
- **"무료" 는 세 종류였고 그중 하나만 내일도 무료다.** 매일 돌아오는 일일 쿼터(CF 10k neurons,
  OpenRouter 50콜), 한 번 쓰면 끝인 월 크레딧(HF Inference Providers **월 $0.10**, 이번 조사
  25콜에 402 로 소진), 이미 0 인 선불 잔액(Gemini 전 모델 `prepayment credits are depleted`,
  Z.ai 비전 전부 1113). 품질 1위였던 HF 의 Qwen3-VL-235B·DeepSeek-V4-Flash-Vision-Exp 는
  2~4초에 만점이었지만 이 이유로 후보에서 빠졌다. **모델 목록에 free 라고 적힌 것과 지속 가능한
  것은 다르고, 가르는 것은 품질이 아니라 쿼터가 리셋되는지 여부다.**
- **같은 쿼터를 메인 턴에 쓰면 하루 14턴에 끝난다.** CF 응답은 `usage.neurons` 를 직접 준다
  (23,229 토큰 = 956 neurons, 입력 1k 토큰당 약 41). hermes 는 `1+1?` 같은 빈 턴 하나가 이미
  **15,255 입력토큰**이라(`--usage-file` 실측) CF 로 돌리면 턴당 약 711 neurons, 10,000 을
  **14턴**에 태운다. 툴을 부르는 턴은 같은 프롬프트를 콜마다 다시 보내니 그보다 빠르게 준다.
  같은 프롬프트를 3회 보내도 `cached_tokens: 0` 이라 **프롬프트 캐시도 없다.** 비전 콜은
  68 neurons 다. 같은 예산에서 **비전 145콜과 채팅 14턴이 맞바꿔진다.** 쿼터제 무료는 프롬프트가
  작은 경로에만 붙이고, 메인·자식 턴은 무제한 무료 레인에 남긴다.
- **툴이 보인다고 도는 게 아니다.** 조사 시작 시점에 `vision_analyze` 는 툴 목록에 멀쩡히 있었고
  `check_vision_requirements()` 도 True 였는데, `llama-local.service` 는 inactive(dead) 라 모든
  호출이 connection refused 였다. 게이트는 **api_key 유무만 보고 엔드포인트 생존은 안 본다.**
  "툴이 있다" 는 "백엔드가 산다" 의 증거가 아니다.
- **hermes 의 `response_format` 자동 복구는 의미가 아니라 문구로 판정한다.** ling 은
  `does not support feature: structured-outputs` 로 400 을 주는데 `_is_structured_output_rejection()`
  은 에러 문자열에서 `response_format` 을 찾는다. venv 에서 직접 호출해 False 를 확인했다.
  자동 재시도가 없으니 `auxiliary.vision.extra_body` 를 비웠다. **복구 로직이 있다는 것과 이
  에러에 걸린다는 것은 별개고, 확인은 예측이 아니라 그 함수를 부르는 것이다.**
- **폴백 엔트리에는 `model` 을 반드시 박는다.** 비워 두면 OpenRouter 레인이 `auxiliary.vision.model`
  에 들어 있던 **gguf 절대경로를 모델명으로** 보낸다(경고 로그로 실증). 로컬 백엔드를 쓰다가
  클라우드로 폴백하는 구성은 이 누수를 항상 안고 있다.
- 부수적으로 확인한 전멸 목록: Groq 는 모델 13개 중 **VLM 0개**(기존 폴백 2단이 없는 모델을
  가리키고 있었다), GitHub Models 는 `410 github_models_retirement_brownout` 으로 은퇴 중,
  Z.ai 무료는 `glm-4.7-flash` 하나인데 `1210 content.type allowed values: ['text']` 로 텍스트 전용.

## 2026-09-16

- DGX hermes 가 **같은 ComfyUI 로 노래도 만든다**. MiniMax Music 3 를 `music_generate` /
  `music_status` 두 툴로 붙였다 (hermes-workspace `claude/comfy-minimax-music-20260916`).
  이미지처럼 프로바이더로 못 붙인 이유는 hermes 에 **music 레지스트리가 없어서**다 — 있는 것은
  image_gen·video_gen·tts·transcription·web_search 다섯이고, 없는 종류는 평범한 툴로 붙인다.
  툴셋은 `web` — 카톡 데몬의 고정 `--toolsets` 문자열에 이미 있어서 데몬을 안 고쳐도 탑승한다.
- **음악의 비용은 그래프가 아니라 곡 길이에 붙는다.** 실측: 60초 상한이 41초 곡에 205초(콜드),
  40초 상한이 23.6초 곡에 108초(웜). 기록에 남아 있던 846초·1159초는 3~4분짜리 곡이었다.
  "음악은 15분" 은 짧은 곡에는 틀린 가정이고, 대기 안내를 길이에 비례로 고쳤다.
- **전달 울타리가 파일 종류를 가른다.** 카톡 데몬의 `[[image: ]]` 는 확장자 검사가 있어 mp3 를
  "이미지가 아니다" 로 거부한다 — 노래는 `[[file: ]]` 로 나가야 한다. 그래서 배달자(`deliver.py`)를
  `--fence`/`--noun` 으로 일반화했다. 같은 이유로 `SaveAudioMP3` 는 128k 고정이다:
  기본 V0 면 6분짜리 곡이 카톡 10MB 첨부 상한을 말없이 넘는다.
- **새 툴은 카톡에는 즉시, 게이트웨이에는 재시작 뒤에 보인다.** 데몬은 턴마다 `hermes -z` 를 새로
  띄우지만 게이트웨이는 장수 프로세스라 기동 시점의 플러그인을 들고 있다. 그리고 둘 다
  `tool_search` 뒤로 접힌다 (25개 선택 중 12개 지연) — 이미 도는 이미지 경로와 같은 상태다.

- 카톡 봇을 hermes 게이트웨이 **네이티브 채널**로 옮길 수 있는지 조사했다. 된다 — 지금 Discord
  자체가 플러그인 경로(`hermes_plugins.discord_platform.adapter`)로 돌고, 데몬이 손으로 만든
  장치 전부에 네이티브 슬롯이 있다. 조사·실측·미결 결정은 hermes-workspace
  [PR #52](https://github.com/BoBeenLee/hermes-workspace/pull/52) 의
  `tasks/2026-09-16-kakao-gateway-platform.md`.
- 전 단계로 배포본 데몬에 `--resume` 를 넣어 before/after 를 쟀다. **끊기던 것은 텍스트가 아니라
  툴 결과였다** — 데몬의 SQL 재조립이 대화록은 이미 이어 주고 있었다. T1 의 툴 인자에만 있던
  사실을 T2 가 묻자 새 세션은 `모름`, 재개 세션은 정확히 답했고 재실행이 없어 42초 → 11초였다.
- 같이 드러난 것 셋: 게이트웨이에 **턴 벽시계 캡이 없다**(`gateway_timeout` 은 idle 전용),
  `observed` 신뢰 경계 분리가 **fail-open** 이며 텔레그램 소유 문자열 리터럴에 걸려 있다,
  그리고 DGX 의 Discord 게이트웨이는 connected 지만 **턴을 한 번도 돈 적이 없다**
  (`gateway_routing` 0행).

## 2026-09-09

- `cad` 가 두 번째 설계를 냈다. `designs/2026-09-09-phone-cradle` — **대상 기기를 고정하지
  않는 첫 설계**다. 맥북 받침대는 `Mac15,7` 하나에 맞춘 치수가 상수였는데, 여기서는 폰 기종을
  안 정하고 "모든 폭을 커버" 를 요구로 받았다. 그래서 **치수 의존을 파라미터 범위가 아니라
  형상으로 없애는** 문제가 됐고, 그 과정에서 이 hub 가 이미 적어 둔 규율("제약을 크기로 쓰기
  전에 그 크기가 어디를 기준으로 한 것인지 먼저 적을 것", 2026-09-06)이 처음으로 설계 자체에
  적용됐다.

- **접촉이 점이냐 면이냐가 치수 의존을 가른다. 그리고 면 접촉은 저절로 생기지 않는다.**
  처음 세운 근거가 틀렸다 — "폰이 립에 앉고 등판에 기대므로 각도는 등판이 정한다" 는 홈 바닥이
  수평이면 성립하지 않는다. 정역학을 풀면 x 방향 균형이 `-N_back·cos(θ) = 0` 이라
  **폰이 등판을 아예 안 누른다.** 앞으로 밀려 립에 앉고, 접촉이 립 안쪽면과 등판 윗모서리
  **두 점**이 되어 각도가 두께에 종속된다. 고치는 값은 하나였다 — 홈 바닥을 등판각만큼 뒤로
  기울여 등판에 수직으로 두면 밑면·뒷면이 둘 다 면으로 닿고 두께가 식에서 사라진다.
  **"모든 X 를 커버" 요구가 오면 범위를 넓히기 전에 X 가 왜 식에 들어오는지를 먼저 푼다.**

- **그 한 값이 미검증 항목 하나를 통째로 없앴다.** 디딤면이 등판에 수직이면 마찰 0 에서도
  평형이 있다. 맥북 받침대의 가장 큰 열린 항목(C-005 "마찰이 실제로 버티는가", 강철 상대
  실측값을 알루미늄에 쓰는 것이 근거였다)이 이 설계에는 **존재하지 않는다.** 근거가 부족할 때
  근거를 더 찾는 것 말고 **그 근거가 필요 없는 형상으로 가는** 길이 있다. 다른 repo 에도
  옮겨 간다 — 검증 못 하는 가정이 설계를 지배하면 가정을 검증하기 전에 가정을 지울 수 있는지 본다.

- **못 고치는 한계가 다른 항의 설계 목표를 정해 줬다.** 이 받침은 1N 안팎에서 책상 위를
  밀려나고, 그걸 고치려면 마찰 0.4 이상이 필요한데 실측 범위 밖이고 고무 패드는 2재질이라
  사용자 제약이 막는다. **부품 하나로는 해가 없다.** 그래서 밑면 길이 목표를 "몇 N 을 버틴다"
  가 아니라 `F_tip >= F_slide` 로 잡았다 — 넘어지기 전에 미끄러지게. 밀려나는 것은 되돌릴 수
  있고 넘어지는 것은 아니다. 근거 없는 목표값(예: 2N)을 못박고 거기 맞추면 밑면만 길어진다.

- **"컴팩트하게" 의 지배 변수를 두 번 잘못 짚었다.** 처음엔 각도라고 했고, 다음엔 계단이라고
  했는데 둘 다 아니었다. 각도는 누름 전도 모멘트에 5% 밖에 기여하지 않고(지배하는 항은 누르는
  높이 `ℓ·cos²θ` 다), 계단은 디딤면 깊이만큼 하중점을 뒤로 민다(1각 120 / 2단 145 / 3단 170mm).
  **어림으로 "이게 지배할 것" 이라고 쓰기 전에 식의 항을 세어 본다.** 두 번 다 계산이
  직관을 뒤집었다 — 가로가 세로보다 3배 안전하고, 무거운 폰이 가벼운 폰보다 안전하다.

- **그리고 그 계산을 근거로 "조절 폭과 컴팩트함은 구조적으로 충돌한다" 고 쓸 뻔했는데, 그건
  한 칸 과했다.** 계단이 밑면을 먹는다는 계산은 맞다. 틀린 것은 **채널이 같은 쪽을 봐야 한다는
  적지도 않은 가정**이었다. 반대를 보게 하면 전도축도 같이 뒤집혀 두 좌석이 밑면을 나눠 쓰지
  않고 각자 전체를 지레팔로 쓴다 — 두 번째 각도가 밑면을 1mm 도 안 늘렸다 (`cad` D-007).
  **"X 와 Y 는 충돌한다" 는 결론은 그 계산이 깔고 있는 배치 가정까지 적어야 쓸 수 있다.**
  D-009(조절 폭 ↔ 안정성)는 진짜 충돌이었지만 이건 아니었고, 둘을 같은 모양으로 본 것이
  이번의 오류다. 방사 배치까지 밀면 좌석 N 개가 전부 같은 지레팔을 쓰는데, 거기서는 값이
  길이가 아니라 **부피**로 청구된다 (8각 176cm³ vs 양단 120cm³) — 충돌이 사라지는 게 아니라
  **다른 축으로 옮겨 간다.**

- **방사 배치까지 가 보니 그 "다른 축" 이 무엇인지가 정확해졌다.** 정팔각으로 만들면 좌석
  여덟 개가 발자국을 한 번만 쓴다 — 어느 면이든 지레팔이 같다. 그런데 **크기를 정하는 것이
  안정성이 아니었다.** 전도는 3~7배 남고, 크기를 정한 것은 **좌석이 림에서 안쪽에 있는데
  다각형의 면은 축으로 갈수록 좁아진다** 는 사실이다. 폰이 자기 면을 넘으면 이웃 벽에 부딪히고,
  그래서 8각은 맞변 210mm 가 필요하다 (4각 119 · 6각 166 · 12각 294). 처음 110mm 로 짰을 때
  여덟 면 전부 그 검사에 걸렸다. **"무엇이 이 치수를 정했나" 를 물으면 대개 예상과 다른 항이
  나온다** — 이 설계에서만 세 번째다 (각도 아님, 계단 아님, 전도도 아님).

- **각도를 지키면서 위치를 무단으로 만들 수 있는데, 그 대가가 접촉 형태다.** 원뿔에 접하는
  평면은 어디서 접하든 축과 같은 각이라 원뿔이면 아무 데나 세워도 각도가 같다. 그런데 접촉이
  모선 하나뿐이라 폰이 그 선을 축으로 흔들린다. 면으로 깎으면 위치가 이산화되는 대신 면 접촉이
  남는다. **이 repo 가 이번에 얻은 자산이 면 접촉이므로 그걸 지키는 쪽을 골랐다** — 새 자유도를
  얻는 거래에서 무엇을 내주는지 먼저 본다.

- **근사를 검사되는 주장으로 바꿨다.** 팔각은 프리즘이 아니라 부피를 닫힌 식으로 못 낸다.
  `cradle.py` 가 쐐기 부피를 적분으로 내고 `build.py` 가 FreeCAD 솔리드와 2% 안에서 일치하는지
  검사해 어긋나면 죽는다. 그 값이 전도 계산의 질량으로 들어가기 때문이다. 내보낸 STL 을 다시
  읽어 경계 상자를 대조하는 규율(2026-09-06)과 같은 모양이고, **대상이 형상이 아니라 계산**이다.

- **형상이 복잡해지면서 잃은 것도 값으로 적었다.** 팔각에서는 OCC 필렛이 통째로 실패한다
  (`StdFail_NotDone`). 프리즘 하나였을 때는 같은 코드가 잘 걸렸다. `fillet_radius` 를 0 으로
  두고 왜 0 인지를 파라미터 주석에 적었다 — **안 되는 것을 조용히 비워 두면 다음 사람이
  다시 시도한다.**

- **레퍼런스에서 값이 아니라 실패 원인을 가져왔다.** print-in-place 힌지는 무단 각도 조절을
